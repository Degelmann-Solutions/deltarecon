# DeltaRecon

Degelmann DeltaRecon is a deterministic method for release-deviation analysis of a Life valuation process chain. After a release, many simultaneous changes to data, parameters and code move results between version N and version N+1. DeltaRecon traces the difference back to its causes on an open reference model.

DeltaRecon is a building block of ActuMesh, a wider concept of an agent layer for actuarial work. DeltaRecon itself uses no agents: every result comes from deterministic runs and comparisons.

The repo currently holds two building blocks: version 3 of the engine-neutral stage contracts for one chain stage, the liability cash-flow projection; and the package `degelmann.deltarecon`, which runs a release of the reference model through the run contract, writes a run record for every run, replays a recorded run, compares two runs per model point through the compare contract, condenses the deviations into a signature table, checks a recorded run against a newer revision, derives the change manifest from the history between the revisions of two recorded runs, walks every state between them to attribute the deviation to revisions, per quantity, and searches the same history by halving it, with fewer runs, checked against the walk. The reference model lives in its own repository, `delib-history`, and a release is a commit of it: release N is its first commit.

## Quick start

You need [uv](https://docs.astral.sh/uv/) 0.13.5 or newer, and Git to make and update the clone of `delib-history`; the commands read the clone with the Python library dulwich, a locked dependency, and need no Git. `uv sync` installs the uv-managed Python 3.14.9 that `.python-version` and `pyproject.toml` pin, if it is absent, and the locked dependencies. The project uses only uv-managed interpreters (`python-preference = "only-managed"` in `pyproject.toml`), never a Python found on `PATH`. An older uv does not know Python 3.14.9, and `uv sync` then fails: uv 0.12.15 does not know it, uv 0.13.5 does; `uv self update` updates it.

```sh
git clone https://github.com/Degelmann-Solutions/deltarecon
cd deltarecon
git clone https://github.com/Degelmann-Solutions/delib-history repositories/delib-history
uv sync
uv run deltarecon request --revision fa368575a66d97c94e96dffc62b273ec95511b12 --label N --run-id run-n-full --output runs/n-full/request.json
uv run deltarecon run runs/n-full/request.json
uv run deltarecon replay runs/n-full/run-record.json
uv run deltarecon regression runs/n-full/run-record.json --revision 887b7181d22550eda2fb52fa1a6bd77376d4eb2e --output runs/regression-n
uv run deltarecon derive runs/n-full/run-record.json runs/regression-n/run/run-record.json --output runs/changes.json
uv run deltarecon search runs/n-full/run-record.json runs/regression-n/run/run-record.json --quantity Bruttobeitrag --periods 0-59 --tolerance profiles/tolerance-bruttobeitrag.json --target-only --output runs/search
```

`uv sync` installs the command `deltarecon`; `uv run python -m degelmann.deltarecon` is the same command. The third line clones the reference model repository to the place where `deltarecon` and the tests read it: `repositories/delib-history` below the working directory. The folder `repositories/` is ignored by Git. Start the commands from the root of this repository, or name the folder that holds the clone of `delib-history` with `--repositories DIR`. After the clone no command uses the network. The tests are not part of the quick start; `uv run pytest -q` runs them. They need the clone and the commits `b64334e09613c45a7a12468dfddc0d9ec47819bb`, `fa368575a66d97c94e96dffc62b273ec95511b12` and `887b7181d22550eda2fb52fa1a6bd77376d4eb2e` in it; without them the test session ends and prints the clone command. A clone made before the newer commits is updated with `git -C repositories/delib-history pull`.

The quick start is pinned: it runs the start commit of the reference chain of `delib-history`, `fa368575a66d97c94e96dffc62b273ec95511b12`, which holds the data, parameters and code of release N with three fixes that make a run faster and keep every result bit for bit, and the newer revision `887b7181d22550eda2fb52fa1a6bd77376d4eb2e`, 32 commits later, the two ends of the reference attribution below, so it gives the same result whatever commits `delib-history` gains later. The label `N` of the older run names release N, whose results the start commit gives. The regression reports the deviation between the two and exits with status 1; the next commands run all the same. The search compares under the tolerance profile `profiles/tolerance-bruttobeitrag.json`, which lets a change of the `Bruttobeitrag` of at most one cent per model point and month pass and compares every other quantity exactly. It narrows to the target `--quantity Bruttobeitrag --periods 0-59`, the first five projection years, needs no walk, and prints its runs, the runs a walk would take, and the runs it saved. It ends with one finding, `interval_not_resolved` for the interval from state 24 to state 28: the changes inside that interval exceed the tolerance only taken together, while neither half differs on its own, so the search attributes nothing for it (see `contracts/v3/localise.md`, "Halving"). With `--target-only` it runs every inner state on the target alone, without the model's checks, while state 0 and the last state stay full runs. The regression run names the start commit as its input data, so the search holds the input data at the start commit: it prints `held: input_data` and does not show the effect of the commit that changes the model point table. The reference attribution below runs both ends from their own requests and moves the input data with the states; the search and that walk differ on purpose. The walk, the check of a search against a walk with `--walk`, and `--reuse-walk` are described with the commands below; the walk of the 33 states of the reference chain takes about 3 minutes on the author's machine. On the author's machine the `uv run` lines of the quick start took about 62 s in the measurement `measurements/2026-10-27-quick-start.json` of 2026-10-27, from fresh clones, under Linux on 24 logical processors: about 2 s for the request, 3 s for the run, 6 s for the replay, 14 s for the regression, 2.5 s for the derivation, and 34 s for the search, which ran 17 states, about 2 s per state, where a walk runs 33, and saved 16. Beside them, and not counted, the two `git clone` lines took about 2 s and `uv sync` about 1 s, with the uv cache and the uv-managed Python already on the machine; on a machine without them `uv sync` downloads both first. The earlier measurement `measurements/2026-10-23-release-itemspaces.json` ran a quick start that also walked every state and ran the tests, on the earlier reference chain from release N to `ab5dc79`, before the fixes, under Python 3.12.13 on the computation path `modelx`, while other work loaded the machine: about two and three quarter hours, of which about 97 minutes for the walk of 36 states and about 57 minutes for the search checked against it. Measured in one process, before the model points were projected in worker processes, a full run of 350 model points held at most about 210 MiB (`measurements/2026-10-23-release-itemspaces.json`); before each model point's ItemSpace was released it held about 8 GiB (`measurements/baseline.json`, the same eight steps under the same load). With worker processes the measurement gives the largest single process of a step, not the sum of all processes: about 230 MiB for the run in `measurements/2026-10-27-quick-start.json`. `uv run python tools/measure_quick_start.py` measures the quick start: it runs the `uv run` commands above one by one from the root of this repository, with a new work folder in place of `runs/` (`runs/measure-<UTC timestamp>`, or `--work DIR`; the output of each step goes to `logs/` in it), and prints the seconds of each step, the peak memory of its largest process, and the cost per state of the search, beside the recorded baseline `measurements/baseline.json`; the total is compared only with a baseline of the same steps. `--steps run` measures one step and the steps it needs, `--output FILE` writes the measurement as JSON, and `--beside NAME=SECONDS` (repeatable), for example `--beside git-clone=12.3 --beside uv-sync=40.1`, records a duration taken outside the tool, prints it below the table and leaves it out of the total. The folder `measurements/` holds the recorded measurements.

- `request` writes a run request with the complete release identity. A release is a commit of `delib-history`: the identity holds one reference for each of the kinds `code_state`, `parameter_set` and `input_data`, all three with the value `git:https://github.com/Degelmann-Solutions/delib-history@<full commit hash>`, and one `engine_version` with the versions of modelx, pandas, numpy and Python. The engine version also names the computation path, and `--path` chooses it: `export`, the default, writes `modelx 0.33.0 export, pandas 3.0.6, numpy 2.5.3, Python 3.14.9` (versions as installed), and the run reads the model with modelx, exports it with `mx.export_model` into its scratch folder, and projects every model point and its checks through the exported package; `modelx` writes `modelx 0.33.0, pandas 3.0.6, numpy 2.5.3, Python 3.14.9` and projects through modelx itself. The model point ids and the parameter inventory are read through modelx on both paths. Both paths compute the same formulas and are meant to give the same export; the tests check this on a subset, the reference walk checks it through its signature tables, and an opt-in guard compares the bits of both paths on every state of the reference chain (see the tests below). A run never falls back to the other path: an export or an import of the exported package that fails ends the run with the outcome `error`. A recorded engine version of another value, from another engine or from a request written before the paths existed, names the path `export` when its first comma-separated part ends with ` export` and `modelx` otherwise; every request written before therefore names the path `modelx` and still runs on it. `--revision` takes a full or a short hash, a branch, a tag, or `HEAD`, and the request holds the full hash of the commit; an ancestry suffix such as `HEAD~1` or `main^` is not read and names no commit; `fa36857...` above is the start commit of the reference chain. A change of the working tree that is not committed cannot be run. Add `--subset RLV-000001 RLV-000002` to run named model points only; the public model point id is the column `policy_id`. Add `--enable <change id> ... --manifest <path>` to enable changes of a change manifest that lies in the folder of the request or below it.
- `run` checks the request, restores the files of the named commit to a scratch folder, projects the selected model points on the computation path the engine version names and evaluates the model's five built-in checks for each. It writes `response.json`, the export `results.csv` and `run-record.json` beside the request. The outcome is `succeeded`, `failed` (a model point raised, a check is false, or a value is not finite; there is no export), `error` (the request was accepted, but the engine could not restore or read the state: `no_model_point`, `invalid_model_point_id`, or `state_not_readable` with the kind of error and the last line of its message, the scratch folder and the repositories folder written as `<scratch>` and `<repositories>`; there is no export) or `rejected` (the request broke a rule, the release identity names no commit of the local clone, or a parameter of the release state is not a finite number; nothing ran). The message of a failed model point is one line, the same on both computation paths. For an output that raised it names the output, the kind of error, the first line of its message and the innermost formula that raised, as modelx names it, with its arguments: `result_cf raised ValueError: invalid sex in RLV_DE_S.Projection[16].sex()`, or `... in RLV_DE_S.Projection[1].lapse_rate(t=3)` for a formula of `t`. Without a formula it names the kind of error and the last line of the message. The problems of one model point, such as `check_prem_split is false`, are joined with `; `. A run record is written for every outcome, except for a request that is not readable as a run request; that one gets the rejected response alone. Each run record names its execution by a `record_id` of the form `record-<random UUID>`; `run_id` names the request. Two runs of one request therefore write the same bytes in every document but the run record. A run projects its model points in worker processes: `--workers N`, else the environment variable `DELTARECON_WORKERS`, else one per processor the process may use, never more than there are points; `N` and the variable must be whole numbers of at least 1, otherwise the command does not start and exits with status 2. The parent process restores the state and, on the path `export`, exports the model once; each worker opens that scratch folder, and the parent keeps the order of the selection. With `--workers 1` the points are projected one after the other in the parent. The worker count is not recorded in any document and changes no byte of one. `replay`, `regression`, `walk` and `search` take `--workers` as well and use it for every state they run.
- `replay` checks a run record, repeats the run in `replay/` beside it, and compares the recorded run with the repeated one through the compare contract. It writes `replay-compare.request.json`, `replay-compare.result.json`, the deviation file `replay-compare.deviations.csv` when the runs are compared, and `replay-record.json`, which lists them. It prints the outcome, the number of deviating coordinates and the paths; the coordinates are in the deviation file. The outcome is `reproduced_exactly`, `reproduced_at_decimals` or `reproduced_within_tolerances`, by what the tolerance profile holds, or `not_reproduced`. A recorded run with the outcome `error` has no export: the replay repeats it and calls it `reproduced_exactly` when the new response is byte for byte the recorded one, apart from `contract_version` for a run recorded under 2.0 or 3.0; nothing is compared. If the record or a file it lists was altered after recording, the clone no longer holds the commit, or the record names neither engine version of the present engine, the replay is rejected and writes nothing. The replay repeats the run on the computation path its engine version names. A run record written under contract version 2.0, 3.0 or 3.1 is replayed; one written under 1.0 is not, the replay rejects it with `unsupported_version`.
- `compare <request>` compares the two runs a compare request names, coordinate by coordinate under the tolerance profile of the request. It writes `compare.result.json` beside the request, the deviation file `compare.deviations.csv` and `signature-table.json` when the outcome is `compared`, and `compare.run-record.json` when the release identities of both runs can be read. A request that is not readable as a compare request writes nothing. Every comparison pairs the values of the two runs by projection period: on the time basis `policy_month`, whose periods count from the issue date, each run counts a model point from its own first exported period, the policy month of its valuation date, so a model point whose valuation month moves between the two runs is still compared month by month of its projection; on any other time basis the periods are compared as they are. The deviation file, the coverage ranges and the signature table therefore write projection periods, while run responses and exports keep policy months. The deviation file is a CSV file with the columns `model_point_id,period,quantity,left,right`, one row per coordinate above tolerance; without a deviation it holds the header alone. The result references it by path and SHA-256 and lists the deviating model points, the added and removed period ranges, the parameter diff of the two run records, and, when the two run records name different engine versions, both versions. A difference `right - left` that is not a finite number rejects the comparison with `non_finite_difference` and names the model points; the result and its record are written, but no deviation file and no table. The signature table has one row per stage and quantity that deviates: deviating model points and coordinates, first and last period, coordinates with the right value above and below the left one, and the largest increase and decrease. It is derived from the compare result and its deviation file alone and holds no timestamp, so the same comparison gives the same bytes.
- `regression <run-record> --revision <commit> --output <folder>` checks a recorded result against a newer revision. It takes the record of a succeeded full run without enabled changes, runs the named commit on the model point table and the selection of the recorded run, and compares the two runs. The record of a target-only run, whose request names a target, is rejected with `target_only_record` before anything runs or is written. It prints "no deviation above tolerance", or the stage, every deviating model point and the signature table. When the new run fails, ends with an error, or is rejected, nothing is compared. `--path export|modelx` chooses the computation path of the new run, as for `request`; it is `export` without the option. The recorded run may come from another engine version or another path: the new run uses the present engine on the chosen path, and the output and the compare result name both versions. Such a comparison mixes the effect of the engine with that of the newer revision; to separate them, first run the regression against the revision of the recorded run, whose deviations are then the effect of the engine alone. The new folder holds a copy of the recorded run in `recorded/`, the new run in `run/`, and the compare files. In the release identity of the new run `code_state` and `parameter_set` name the newer commit and `input_data` the commit of the recorded run. `--label <text>` sets the label of that release; it is `regression` otherwise. In the quick start the newer revision is `887b7181d22550eda2fb52fa1a6bd77376d4eb2e`, 32 commits after the start commit on the main line of `delib-history`; the run reports what they change in the result and exits with status 1.
- `derive <older-record> <newer-record> --output <file>` derives the change manifest of the history between two recorded runs. It takes the records of two succeeded full runs without enabled changes, the older one first, and refuses the record of a target-only run with `target_only_record`. It reads the revision of each from `code_state` and `parameter_set` of its release identity. The manifest lists one change per commit on the main line after the older revision, up to the newer one, in the order of the history; the main line is the chain of first parents, so a merged branch is one change, the merge. Each change has the commit hash as its id, the log message as its description, the change before it as its only prerequisite, and the realisation type `revision`. Its `class` is a list in the order `data`, `parameter`, `code`, taken from the paths the commit touches: `risikolebensversicherung/model_point_table.csv` is `data`, every other CSV file directly in `risikolebensversicherung/` is `parameter`, everything under `risikolebensversicherung/RLV_DE_S/` is `code`, and a commit that touches none of them has the empty list. A reference that no commit fixes and that differs between the two records, the engine version, is named under `history.remainder` and attributed to no change. The same two records give the same bytes: the manifest holds no timestamp and no path. The folder of `--output` must exist. The command prints the changes and the remainder. Two revisions that are not on one main line, also two records in the wrong order, are refused with `unrelated_revisions`, and a revision the clone does not hold with `unknown_reference`; nothing is written then. In the quick start the regression run of `887b718...` is the newer record. A run may enable a prefix of a derived manifest: the reference engine restores the commit of the last enabled change, and a set that skips a commit is rejected with `unmet_prerequisite`. A change of the type `revision` stands only in a manifest with `history`.
- `walk <older-record> <newer-record> --output <folder>` attributes the deviation between two recorded results to the commits between them. It takes the same two records as `derive`, which must hold the same selection, derives the manifest, and runs every state on that selection: state 0 is the older commit, state k the state after the k-th commit of the manifest, run as a request that enables the first k changes, on the computation path of the older record, by the rule of `request` above. It checks state 0 against the older and the last state against the newer record; each must reproduce its record under the tolerance profile, exactly without one. It compares each state with the state before it and writes `walk.result.json`: per commit and quantity whether it contributes (a coordinate above tolerance, or an added or removed one), the signed sum of the differences over every coordinate, a missing coordinate counted as 0, the sum of their absolute values, and the signature row. The sums are exact and written rounded once to binary64; the signed sums of a quantity add up exactly to the deviation between the two records when the walk compares exactly, and otherwise to the difference of the last state and state 0, which reproduce the records only within the tolerances. The input data moves with the states when each record names its own commit as input data, and is held at the older commit when both name the same one, as a record of `regression` does; the walk result then names the `data` commits whose effect on the input it does not show. Records whose references do not fit the history are refused with `reference_mismatch`, records of different selections with `selection_mismatch`, before anything runs; the refusals of `derive` apply as well. A state that ends `failed`, `rejected` or `error` is a finding, and the next state that runs carries its commit. The new folder holds the manifest, copies of the two recorded runs in `older/` and `newer/`, one folder per state, the comparisons of the steps that contribute and of an end that is not reproduced, `walk.result.json`, and `walk.run-record.json`. The same two records give the same `walk.result.json`, byte for byte. The command prints the two ends, the held input, the remainder, the contributing quantities of each step, and the findings. The contract of the walk is [`contracts/v3/localise.md`](contracts/v3/localise.md).
- `search <older-record> <newer-record> --output <folder>` finds the commits that contribute with fewer runs than a walk. It takes the same two records, makes the same checks before the first run, and needs no walk. It runs state 0 and the last state and checks them against the two records, then halves the history: an interval of states is judged by comparing its two end states under the tolerance profile, an interval whose ends agree is not divided further, and an interval of one commit whose ends differ is a contribution, with the sums of a walk step. A midpoint that does not run is replaced by the nearest state inside the interval that runs. `--quantity NAME` (repeatable) and `--periods FIRST-LAST` (inclusive, in months counted from the valuation date, so period 0 is the first projection month of every model point, in force or new, counted in each state from that state's own valuation month of the model point) narrow the search to a target, for example `--quantity Bruttobeitrag --periods 0-59` for the first five projection years; only the target's coordinates are judged and summed, and a failure outside the target does not change the judgement. Without them, or with a `--quantity` for every quantity and no `--periods`, the search covers every coordinate, and each contribution holds the signature row of every quantity it contributes to. It writes `search.result.json`: the target, the intervals judged, the contributions, the findings, among them `interval_not_resolved` for an interval whose ends differ while neither half does, and the runs of the search, the n + 1 runs of a walk, and the runs saved. `--walk <folder>` checks the search against a walk folder of the same two records: the search refuses a walk that does not attribute every commit with `walk_not_attributed`, and a walk of other records, another tolerance profile, another history, or another engine version, also another computation path, or one whose folder fails its reader rules, among them a state whose request names a target, with `walk_mismatch`, before anything runs. It copies the walk into `walk/` and names per commit and quantity the contributions of the walk it missed. `--reuse-walk`, only with `--walk`, takes every state the search needs from that copy instead of running it: the walk has already run each state on the request the search would send on the present engine, so the findings are the same; a reused state is no run, the search prints how many states it reused, and its result and run record name the switch `reuse_walk`. `--target-only`, only with a narrowed target (`--quantity` for a proper subset of the quantities, or `--periods`), runs every inner state the search runs itself on the target alone, without the model's checks, while state 0 and the last state stay full runs; the comparison kept for a contribution is then on the target only, a full state compared through its target view `state-<k>.target/`, a derived response and export that is no run, and the result and run record name the switch `target_only`; it may be combined with `--reuse-walk`. The exit status is 0 when both ends ran and are reproduced, also with missed contributions; the walk stays the reference result.

Read a walk result with its limits in mind. A contribution belongs to a commit in the order of the history: a commit whose effect a later commit overrides keeps its own step, and an interaction of two commits lands on the later one; another order could attribute differently. A state that does not run is reported as a finding, and its contribution is attributed to the next state that runs, together with that state's own. Inputs the history does not version are not attributed, and an input both results were calculated on is held even when the history versions it: the walk then does not show the effect of the commits on that input. The engine version is not attributed either: every state runs on the present engine, on the computation path of the older record, and a differing engine version of a record is named as remainder. A search has the same limits and one more: it does not see contributions that cancel within one interval, such as a commit and its revert, or two commits whose effects on the target offset each other; only the walk sees them. A search checked against a walk names them as missed.

There is no default tolerance profile. `compare` takes the profile of its request. `replay`, `regression`, `walk` and `search` compare exactly unless `--tolerance <file>` names a profile: a JSON file in the form of the `tolerance` member of a compare request, for example `{"per_quantity": {"Provisionen": {"decimals": 2, "upper": {"abs_tol": 0, "rel_tol": 0}, "lower": {"abs_tol": 0, "rel_tol": 0}, "derivation": "Commissions are settled in whole cents."}}}`.

The exit status is 0 only for a succeeded run, a reproduced replay, a comparison or a regression run that reports no deviation, a written request or manifest, a walk that attributes every commit, also with findings of intermediate states, and a search whose two ends are reproduced, also with missed contributions. It is 1 for a failed or rejected run or one that ends with an error, a replay that is not reproduced, a comparison or a regression run with a deviation, an added or removed coordinate, or the outcome `incompatible` or `rejected`, a manifest that cannot be derived, a walk that is refused or leaves a commit unattributed because state 0 or the last state does not run or is not reproduced, a search that is refused or stops, a regression, derivation, walk or search given the record of a target-only run, which is refused with `target_only_record`, and a request or regression whose revision, release, or clone the repositories do not hold. It is 2 when a command cannot start: an output exists already, the tolerance file or the target of a search is faulty, the record is not that of a succeeded run, apart from a target-only run (for a replay: of a succeeded run or one that ended with an error), or the clone is a shallow one whose history is cut off. No command overwrites an existing file, and a run only reads the clone: it reads the committed files from the object store, makes no checkout and no fetch, and applies enabled changes to the scratch folder. The path of a text patch is relative to the root of `delib-history`, for example `risikolebensversicherung/lapse_table.csv`. `runs/` is a free choice; run documents may live in any folder.

On the author's machine the full run of the 350 model points on the export path takes, command start included, about 15 s with `--workers 1` and about 4 to 7 s with the default of 24 workers (measured on 2026-10-25); a subset run of a few points takes a few seconds.

The output of the search is pinned as well: `measurements/quick-start-search.SHA256SUMS` lists the SHA-256 of `search.result.json` and of every file it hashes, the change manifest `changes.json`, the response and results of each state the search ran, and the compare result and deviation file of each contribution, with paths relative to the search folder. `cd runs/search && sha256sum -c ../../measurements/quick-start-search.SHA256SUMS` compares a search folder with the pin; every listed file must report `OK`. The run records (`run-record.json`, `*.run-record.json`, `search.run-record.json`) are not pinned: each holds the time it was recorded and a random record id, so no two runs write the same bytes. The other files the search writes are not listed, because the search result does not hash them.

## Reproduce the reference attribution

The folder `oracle/` publishes the reference attribution of the history of `delib-history` from the start commit of its reference chain, `fa368575a66d97c94e96dffc62b273ec95511b12`, which holds release N on the fixed model, to `887b7181d22550eda2fb52fa1a6bd77376d4eb2e`: the two run requests, `n.request.json` (run id `oracle-n`, label `N`) and `n1.request.json` (run id `oracle-n1`, label `N+1`), both under contract version 3.1 and on all 350 model points, and `SHA256SUMS`, the SHA-256 of the `walk.result.json` of the walk between them and of every signature table the walk writes, one per step that contributes. The walk compares under the tolerance profile `profiles/tolerance-bruttobeitrag.json`. To reproduce it from fresh clones:

```sh
git clone https://github.com/Degelmann-Solutions/deltarecon
cd deltarecon
git clone https://github.com/Degelmann-Solutions/delib-history repositories/delib-history
uv sync
mkdir -p runs/oracle-n runs/oracle-n1
cp oracle/n.request.json runs/oracle-n/request.json
cp oracle/n1.request.json runs/oracle-n1/request.json
uv run deltarecon run runs/oracle-n/request.json
uv run deltarecon run runs/oracle-n1/request.json
uv run deltarecon walk runs/oracle-n/run-record.json runs/oracle-n1/run-record.json --tolerance profiles/tolerance-bruttobeitrag.json --output runs/oracle-walk
cd runs/oracle-walk
sha256sum -c ../../oracle/SHA256SUMS
```

On macOS the last command is `shasum -a 256 -c ../../oracle/SHA256SUMS`. Every listed file must report `OK`. The two runs take about 3 s each and the walk of 33 states about 3 minutes.

The requests name the engine version `modelx 0.33.0 export, pandas 3.0.6, numpy 2.5.3, Python 3.14.9`, the export path. `uv sync` installs it: the uv-managed Python 3.14.9 and the packages locked in `uv.lock`, as described at the top of this README. Under another Python patch release or another package version `run` rejects the request with `unknown_reference`, because the request names another engine version than the present one; nothing runs. The engine version is part of every run response, and `walk.result.json` holds the SHA-256 of the responses, so its hash depends on the exact engine; the signature tables do not name it. The hashes were computed under Linux on x86-64, in a clean worktree of this repository's commit that publishes contract version 3.1, `7b0a078`, and a local clone of `delib-history` that holds the reference chain from `fa36857` to `887b718`; whether other hardware gives the same bytes is not yet checked. [`oracle/REPRODUCTIONS.md`](oracle/REPRODUCTIONS.md) records every reproduction with its machine, engine version and revisions. `DELTARECON_ORACLE=1 uv run pytest tests/test_oracle.py -q` runs the reproduction in a temporary folder and checks every listed hash, and that every signature table, with its contract version set back to `3.0`, hashes to the digest the archive of 2026-10-27 lists, and, rebuilt in policy months from the deviation file of its step (each period plus the first exported period of its model point in the step's left state) and with its contract version set back to `2.0`, to the digest the archive of 2026-10-22 lists; without the variable only the published files are checked.

The folder [`oracle/archive/2026-10-27/`](oracle/archive/2026-10-27/) keeps the oracle published on 2026-10-27, unchanged: its requests under contract version 3.0, its `SHA256SUMS` and its `REPRODUCTIONS.md`, which records its computations and the reproduction of 2026-10-27 from fresh clones of both repositories, in which every listed file reported `OK`. The present tool writes 3.1, so its walk result and signature tables differ from the archived ones in `contract_version` alone; the walk result also holds the hashes of the 3.1 responses. The signature tables are otherwise the archived ones, byte for byte.

The folder [`oracle/archive/2026-10-22/`](oracle/archive/2026-10-22/) keeps the oracle published on 2026-10-22, unchanged: its requests under contract version 2.0, its `SHA256SUMS` and its `REPRODUCTIONS.md`, which records the computation under Linux and the reproduction under Windows on the same hardware. It is a record and is reproduced with deltarecon at commit `a53516d`, which writes 2.0. The present tool writes 3.1 and compares on projection periods, so its walk result and signature tables differ from the archived ones in `contract_version` and the period numbering; the walk result also holds the hashes of the 3.1 responses. The signature tables are otherwise the archived ones, field for field.

The earlier bare runner, which projects every model point and prints one SHA-256 over all result frames, moved to `delib-history` as `tools/run_release.py`, together with the portfolio builder and the test that pins the result hash of release N.

## Stage contracts

[`contracts/v3/`](contracts/v3/README.md) describes the stage `liability_cashflow` by three contracts that any calculation engine can implement: run, changes and compare. A domain reference names the quantities, their units and signs, and the time basis. A fourth file, `localise.md`, is no stage contract and no engine implements it: it fixes the walk and the search, procedures of the tool built on the three, and their results. The pack stands alone and names no engine and no implementation language. It holds the contract text, JSON schemas, and small synthetic examples of accepted and rejected input.

The tool writes contract version 3.1 and reads documents of 1.0, 2.0, 3.0 and 3.1, each against the schemas of its own version; the pack `contracts/v3/` holds the schemas of 3.0 and 3.1. A run record written under 1.0, 2.0 or 3.0 serves as input to `regression`, `derive`, `walk`, `search`, and a comparison of recorded runs. `replay` repeats a run recorded under 2.0, 3.0 or 3.1 and rejects one recorded under 1.0 with `unsupported_version`. A walk folder written under 1.0, 2.0 or 3.0 is a reference for `search --walk`. [`contracts/v3/README.md`](contracts/v3/README.md#changes-from-30) lists the changes from 3.0 and [from 2.0](contracts/v3/README.md#changes-from-20); those from 1.0 to 2.0 are in [`contracts/v2/README.md`](contracts/v2/README.md#changes-from-10).

The pack is a specification. `degelmann.deltarecon` implements the run contract and the changes contract for the reference model, and the compare contract for any two runs: the comparison reads documents and exports and knows no engine. A replay goes through the compare contract and writes a compare result.

## The reference model and its limits

The reference model is `RLV_DE_S`, the Risikolebensversicherung (German term life) model from the `delib` library of [lifelib](https://github.com/lifelib-dev/lifelib). It is kept in the repository `delib-history`, in the folder `risikolebensversicherung/`. It projects monthly liability cash flows per model point. [modelx](https://github.com/fumitoh/modelx) reads it and runs it, through its export `mx.export_model` on the default computation path or itself on the path `modelx`.

Read every result from this model with these limits in mind:

- It is a demonstration of mechanics, not a valuation model. Upstream marks the library as a draft.
- The biometric tables are proxies. The mortality table is a Gompertz-form stand-in for DAV 2008 T, which is not public and is not shipped. Lapse rates are upstream's own assumptions.
- The cash flows are gross and undiscounted.
- The statutory references in the model's documentation are unverified upstream.
- DeltaRecon claims no HGB reserve, no Zinszusatzreserve and no profit participation from this model.

The portfolio holds upstream's 14 model points unchanged, plus 336 generated points, 24 variants of each. A variant keeps its template's product features and varies term, issue age, sex, smoker status, sum assured, premium frequency and, for two lives, the age gap and the second life's smoker status. One third of the generated points are in force, after one completed year, at 40 and 70 percent of the term, and in the final year; the others are new business. Each dimension is balanced within a template and mixed independently of the others, so a change in one input can be told apart from the others. Generated points stay inside upstream's documented product envelope (issue age 18 to 65, end age at most 75, term 5 to 40 years) and reach its edges.

The portfolio is synthetic and contains no client data. It is built to exercise the model's mechanics, not to resemble a real book: in-force points carry issue dates back to 1987, and the model prices all of them on its one current basis.

## Upstream attribution

This repo holds no file of lifelib. The reference model repository `delib-history` does: at release N the model files and five of its six input CSVs are copied byte for byte from lifelib at commit `fb1d195ab5423031cfd6d2548fe25a86b76cd0a1`, under the MIT licence, "Copyright (c) 2022 lifelib Developers". The sixth CSV, `model_point_table.csv`, extends upstream's file. Later commits of `delib-history` change some of these files; they are the changes that a derived manifest lists. `UPSTREAM.md` in the folder `risikolebensversicherung/` of `delib-history` records the details.
