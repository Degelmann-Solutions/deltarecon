# DeltaRecon

Degelmann DeltaRecon is a deterministic method for release-deviation analysis of a Life valuation process chain. After a release, many simultaneous changes to data, parameters and code move results between version N and version N+1. DeltaRecon traces the difference back to its causes on an open reference model.

DeltaRecon is a building block of ActuMesh, a wider concept of an agent layer for actuarial work. DeltaRecon itself uses no agents: every result comes from deterministic runs and comparisons.

The repo currently holds two building blocks: version 2 of the engine-neutral stage contracts for one chain stage, the liability cash-flow projection; and the package `degelmann.deltarecon`, which runs a release of the reference model through the run contract, writes a run record for every run, replays a recorded run, compares two runs per model point through the compare contract, condenses the deviations into a signature table, checks a recorded run against a newer revision, derives the change manifest from the history between the revisions of two recorded runs, walks every state between them to attribute the deviation to revisions, per quantity, and searches the same history by halving it, with fewer runs, checked against the walk. The reference model lives in its own repository, `delib-history`, and a release is a commit of it: release N is its first commit.

## Quick start

You need Git and [uv](https://docs.astral.sh/uv/). `uv sync` fetches Python 3.12 if it is absent and installs the locked dependencies.

```sh
git clone https://github.com/Degelmann-Solutions/deltarecon
cd deltarecon
git clone https://github.com/Degelmann-Solutions/delib-history repositories/delib-history
uv sync
uv run deltarecon request --revision b64334e09613c45a7a12468dfddc0d9ec47819bb --label N --run-id run-n-full --output runs/n-full/request.json
uv run deltarecon run runs/n-full/request.json
uv run deltarecon replay runs/n-full/run-record.json
uv run deltarecon regression runs/n-full/run-record.json --revision ab5dc790f5bed52f94a4c8fb8d6b710bc31f0a33 --output runs/regression-n
uv run deltarecon derive runs/n-full/run-record.json runs/regression-n/run/run-record.json --output runs/changes.json
uv run deltarecon walk runs/n-full/run-record.json runs/regression-n/run/run-record.json --tolerance profiles/tolerance-bruttobeitrag.json --output runs/walk
uv run deltarecon search runs/n-full/run-record.json runs/regression-n/run/run-record.json --quantity Bruttobeitrag --periods 0-59 --tolerance profiles/tolerance-bruttobeitrag.json --walk runs/walk --output runs/search
uv run pytest -q
```

`uv sync` installs the command `deltarecon`; `uv run python -m degelmann.deltarecon` is the same command. The third line clones the reference model repository to the place where `deltarecon` and the tests read it: `repositories/delib-history` below the working directory. The folder `repositories/` is ignored by Git. Start the commands from the root of this repository, or name the folder that holds the clone of `delib-history` with `--repositories DIR`. After the clone no command uses the network. The tests need the clone and the commits `b64334e09613c45a7a12468dfddc0d9ec47819bb` and `ab5dc790f5bed52f94a4c8fb8d6b710bc31f0a33` in it; without them the test session ends and prints the clone command. A clone made before the newer commit is updated with `git -C repositories/delib-history pull`.

The quick start is pinned: it runs release N, `b64334e09613c45a7a12468dfddc0d9ec47819bb`, and the newer revision `ab5dc790f5bed52f94a4c8fb8d6b710bc31f0a33`, the two ends of the reference attribution below, so it gives the same result whatever commits `delib-history` gains later. The regression reports the deviation between the two and exits with status 1; the next commands run all the same. The walk and the search compare under the tolerance profile `profiles/tolerance-bruttobeitrag.json`, which lets a change of the `Bruttobeitrag` of at most one cent per model point and month pass and compares every other quantity exactly. The search narrows to the target `--quantity Bruttobeitrag --periods 0-59`, the first five projection years, and prints its runs, the runs of a walk, and the runs it saved. The regression run names release N as its input data, so the walk and the search hold the input data at release N: the walk prints `held: input_data` and does not show the effect of the commit that changes the model point table. The reference attribution below runs both ends from their own requests and moves the input data with the states; the two walks differ on purpose. On the author's machine the quick start took about two hours, measured while a second walk ran beside it: about 100 s each for the run, the replay and the regression, about an hour for the walk of 36 states, about 45 minutes for the search, which ran 23 states and saved 13 runs, and about five minutes for the tests.

- `request` writes a run request with the complete release identity. A release is a commit of `delib-history`: the identity holds one reference for each of the kinds `code_state`, `parameter_set` and `input_data`, all three with the value `git:https://github.com/Degelmann-Solutions/delib-history@<full commit hash>`, and one `engine_version` with the versions of modelx, pandas, numpy and Python. `--revision` takes any name of a commit in the clone, `HEAD`, a branch or a short hash, and the request holds the full hash; `b64334e...` above is release N. A change of the working tree that is not committed cannot be run. Add `--subset RLV-000001 RLV-000002` to run named model points only; the public model point id is the column `policy_id`. Add `--enable <change id> ... --manifest <path>` to enable changes of a change manifest that lies in the folder of the request or below it.
- `run` checks the request, restores the files of the named commit to a scratch folder, projects the selected model points and evaluates the model's five built-in checks for each. It writes `response.json`, the export `results.csv` and `run-record.json` beside the request. The outcome is `succeeded`, `failed` (a model point raised, a check is false, or a value is not finite; there is no export), `error` (the request was accepted, but the engine could not restore or read the state: `no_model_point`, `invalid_model_point_id`, or `state_not_readable` with the kind of error and the last line of its message, the scratch folder and the repositories folder written as `<scratch>` and `<repositories>`; there is no export) or `rejected` (the request broke a rule, the release identity names no commit of the local clone, or a parameter of the release state is not a finite number; nothing ran). A run record is written for every outcome, except for a request that is not readable as a run request; that one gets the rejected response alone. Each run record names its execution by a `record_id` of the form `record-<random UUID>`; `run_id` names the request. Two runs of one request therefore write the same bytes in every document but the run record.
- `replay` checks a run record, repeats the run in `replay/` beside it, and compares the recorded run with the repeated one through the compare contract. It writes `replay-compare.request.json`, `replay-compare.result.json`, the deviation file `replay-compare.deviations.csv` when the runs are compared, and `replay-record.json`, which lists them. It prints the outcome, the number of deviating coordinates and the paths; the coordinates are in the deviation file. The outcome is `reproduced_exactly`, `reproduced_at_decimals` or `reproduced_within_tolerances`, by what the tolerance profile holds, or `not_reproduced`. A recorded run with the outcome `error` has no export: the replay repeats it and calls it `reproduced_exactly` when the new response is byte for byte the recorded one; nothing is compared. If the record or a file it lists was altered after recording, the clone no longer holds the commit, or the record names another engine version than the present one, the replay is rejected and writes nothing. A run record written under contract version 1.0 is not replayed; the replay rejects it with `unsupported_version`.
- `compare <request>` compares the two runs a compare request names, coordinate by coordinate under the tolerance profile of the request. It writes `compare.result.json` beside the request, the deviation file `compare.deviations.csv` and `signature-table.json` when the outcome is `compared`, and `compare.run-record.json` when the release identities of both runs can be read. A request that is not readable as a compare request writes nothing. The deviation file is a CSV file with the columns `model_point_id,period,quantity,left,right`, one row per coordinate above tolerance; without a deviation it holds the header alone. The result references it by path and SHA-256 and lists the deviating model points, the added and removed period ranges, the parameter diff of the two run records, and, when the two run records name different engine versions, both versions. A difference `right - left` that is not a finite number rejects the comparison with `non_finite_difference` and names the model points; the result and its record are written, but no deviation file and no table. The signature table has one row per stage and quantity that deviates: deviating model points and coordinates, first and last period, coordinates with the right value above and below the left one, and the largest increase and decrease. It is derived from the compare result and its deviation file alone and holds no timestamp, so the same comparison gives the same bytes.
- `regression <run-record> --revision <commit> --output <folder>` checks a recorded result against a newer revision. It takes the record of a succeeded run without enabled changes, runs the named commit on the model point table and the selection of the recorded run, and compares the two runs. It prints "no deviation above tolerance", or the stage, every deviating model point and the signature table. When the new run fails, ends with an error, or is rejected, nothing is compared. The recorded run may come from another engine version: the new run uses the present engine, and the output and the compare result name both versions. Such a comparison mixes the effect of the engine with that of the newer revision; to separate them, first run the regression against the revision of the recorded run, whose deviations are then the effect of the engine alone. The new folder holds a copy of the recorded run in `recorded/`, the new run in `run/`, and the compare files. In the release identity of the new run `code_state` and `parameter_set` name the newer commit and `input_data` the commit of the recorded run. `--label <text>` sets the label of that release; it is `regression` otherwise. In the quick start the newer revision is `ab5dc790f5bed52f94a4c8fb8d6b710bc31f0a33`, 35 commits after release N on the main line of `delib-history`; the run reports what they change in the result and exits with status 1.
- `derive <older-record> <newer-record> --output <file>` derives the change manifest of the history between two recorded runs. It takes the records of two succeeded runs without enabled changes, the older one first, and reads the revision of each from `code_state` and `parameter_set` of its release identity. The manifest lists one change per commit on the main line after the older revision, up to the newer one, in the order of the history; the main line is the chain of first parents, so a merged branch is one change, the merge. Each change has the commit hash as its id, the log message as its description, the change before it as its only prerequisite, and the realisation type `revision`. Its `class` is a list in the order `data`, `parameter`, `code`, taken from the paths the commit touches: `risikolebensversicherung/model_point_table.csv` is `data`, every other CSV file directly in `risikolebensversicherung/` is `parameter`, everything under `risikolebensversicherung/RLV_DE_S/` is `code`, and a commit that touches none of them has the empty list. A reference that no commit fixes and that differs between the two records, the engine version, is named under `history.remainder` and attributed to no change. The same two records give the same bytes: the manifest holds no timestamp and no path. The folder of `--output` must exist. The command prints the changes and the remainder. Two revisions that are not on one main line, also two records in the wrong order, are refused with `unrelated_revisions`, and a revision the clone does not hold with `unknown_reference`; nothing is written then. In the quick start the regression run of `ab5dc790...` is the newer record. A run may enable a prefix of a derived manifest: the reference engine restores the commit of the last enabled change, and a set that skips a commit is rejected with `unmet_prerequisite`. A change of the type `revision` stands only in a manifest with `history`.
- `walk <older-record> <newer-record> --output <folder>` attributes the deviation between two recorded results to the commits between them. It takes the same two records as `derive`, which must hold the same selection, derives the manifest, and runs every state on that selection: state 0 is the older commit, state k the state after the k-th commit of the manifest, run as a request that enables the first k changes. It checks state 0 against the older and the last state against the newer record; each must reproduce its record under the tolerance profile, exactly without one. It compares each state with the state before it and writes `walk.result.json`: per commit and quantity whether it contributes (a coordinate above tolerance, or an added or removed one), the signed sum of the differences over every coordinate, a missing coordinate counted as 0, the sum of their absolute values, and the signature row. The sums are exact and written rounded once to binary64; the signed sums of a quantity add up exactly to the deviation between the two records when the walk compares exactly, and otherwise to the difference of the last state and state 0, which reproduce the records only within the tolerances. The input data moves with the states when each record names its own commit as input data, and is held at the older commit when both name the same one, as a record of `regression` does; the walk result then names the `data` commits whose effect on the input it does not show. Records whose references do not fit the history are refused with `reference_mismatch`, records of different selections with `selection_mismatch`, before anything runs; the refusals of `derive` apply as well. A state that ends `failed`, `rejected` or `error` is a finding, and the next state that runs carries its commit. The new folder holds the manifest, copies of the two recorded runs in `older/` and `newer/`, one folder per state, the comparisons of the steps that contribute and of an end that is not reproduced, `walk.result.json`, and `walk.run-record.json`. The same two records give the same `walk.result.json`, byte for byte. The command prints the two ends, the held input, the remainder, the contributing quantities of each step, and the findings. The contract of the walk is [`contracts/v2/localise.md`](contracts/v2/localise.md).
- `search <older-record> <newer-record> --output <folder>` finds the commits that contribute with fewer runs than a walk. It takes the same two records, makes the same checks before the first run, and needs no walk. It runs state 0 and the last state and checks them against the two records, then halves the history: an interval of states is judged by comparing its two end states under the tolerance profile, an interval whose ends agree is not divided further, and an interval of one commit whose ends differ is a contribution, with the sums of a walk step. A midpoint that does not run is replaced by the nearest state inside the interval that runs. `--quantity NAME` (repeatable) and `--periods FIRST-LAST` (inclusive, in months counted from the valuation date, so period 0 is the first projection month of every model point, in force or new) narrow the search to a target, for example `--quantity Bruttobeitrag --periods 0-59` for the first five projection years; only the target's coordinates are judged and summed, and a failure outside the target does not change the judgement. Without them, or with a `--quantity` for every quantity and no `--periods`, the search covers every coordinate, and each contribution holds the signature row of every quantity it contributes to. It writes `search.result.json`: the target, the intervals judged, the contributions, the findings, among them `interval_not_resolved` for an interval whose ends differ while neither half does, and the runs of the search, the n + 1 runs of a walk, and the runs saved. `--walk <folder>` checks the search against a walk folder of the same two records: the search refuses a walk that does not attribute every commit with `walk_not_attributed`, and a walk of other records, another tolerance profile, another history, or another engine version, or one whose folder fails its reader rules, with `walk_mismatch`, before anything runs. It copies the walk into `walk/` and names per commit and quantity the contributions of the walk it missed. The exit status is 0 when both ends ran and are reproduced, also with missed contributions; the walk stays the reference result.

Read a walk result with its limits in mind. A contribution belongs to a commit in the order of the history: a commit whose effect a later commit overrides keeps its own step, and an interaction of two commits lands on the later one; another order could attribute differently. A state that does not run is reported as a finding, and its contribution is attributed to the next state that runs, together with that state's own. Inputs the history does not version are not attributed, and an input both results were calculated on is held even when the history versions it: the walk then does not show the effect of the commits on that input. The engine version is not attributed either: every state runs on the present engine, and a differing engine version of a record is named as remainder. A search has the same limits and one more: it does not see contributions that cancel within one interval, such as a commit and its revert, or two commits whose effects on the target offset each other; only the walk sees them. A search checked against a walk names them as missed.

There is no default tolerance profile. `compare` takes the profile of its request. `replay`, `regression`, `walk` and `search` compare exactly unless `--tolerance <file>` names a profile: a JSON file in the form of the `tolerance` member of a compare request, for example `{"per_quantity": {"Provisionen": {"decimals": 2, "upper": {"abs_tol": 0, "rel_tol": 0}, "lower": {"abs_tol": 0, "rel_tol": 0}, "derivation": "Commissions are settled in whole cents."}}}`.

The exit status is 0 only for a succeeded run, a reproduced replay, a comparison or a regression run that reports no deviation, a written request or manifest, a walk that attributes every commit, also with findings of intermediate states, and a search whose two ends are reproduced, also with missed contributions. It is 1 for a failed or rejected run or one that ends with an error, a replay that is not reproduced, a comparison or a regression run with a deviation, an added or removed coordinate, or the outcome `incompatible` or `rejected`, a manifest that cannot be derived, a walk that is refused or leaves a commit unattributed because state 0 or the last state does not run or is not reproduced, and a search that is refused or stops. It is 2 when a command cannot start: an output exists already, the tolerance file or the target of a search is faulty, the record is not that of a succeeded run (for a replay: of a succeeded run or one that ended with an error), or the clone is a shallow one whose history is cut off. No command overwrites an existing file, and a run only reads the clone: it reads the committed files from the object store, makes no checkout and no fetch, and applies enabled changes to the scratch folder. The path of a text patch is relative to the root of `delib-history`, for example `risikolebensversicherung/lapse_table.csv`. `runs/` is a free choice; run documents may live in any folder. If Git is not installed, a command does not start and exits with status 2.

The full run of the 350 model points takes about 80 s on the author's machine, a subset run of a few points a few seconds.

## Reproduce the reference attribution

The folder `oracle/` publishes the reference attribution of the history of `delib-history` from release N, `b64334e09613c45a7a12468dfddc0d9ec47819bb`, to `ab5dc790f5bed52f94a4c8fb8d6b710bc31f0a33`: the two run requests, `n.request.json` (run id `oracle-n`, label `N`) and `n1.request.json` (run id `oracle-n1`, label `N+1`), both under contract version 2.0 and on all 350 model points, and `SHA256SUMS`, the SHA-256 of the `walk.result.json` of the walk between them and of every signature table the walk writes, one per step that contributes. The walk compares under the tolerance profile `profiles/tolerance-bruttobeitrag.json`. To reproduce it from fresh clones:

```sh
git clone https://github.com/Degelmann-Solutions/deltarecon
cd deltarecon
git clone https://github.com/Degelmann-Solutions/delib-history repositories/delib-history
uv sync --python 3.12.13
mkdir -p runs/oracle-n runs/oracle-n1
cp oracle/n.request.json runs/oracle-n/request.json
cp oracle/n1.request.json runs/oracle-n1/request.json
uv run deltarecon run runs/oracle-n/request.json
uv run deltarecon run runs/oracle-n1/request.json
uv run deltarecon walk runs/oracle-n/run-record.json runs/oracle-n1/run-record.json --tolerance profiles/tolerance-bruttobeitrag.json --output runs/oracle-walk
cd runs/oracle-walk
sha256sum -c ../../oracle/SHA256SUMS
```

On macOS the last command is `shasum -a 256 -c ../../oracle/SHA256SUMS`. Every listed file must report `OK`. The two runs take about 100 s each and the walk of 36 states about an hour.

The requests name the engine version `modelx 0.33.0, pandas 3.0.6, numpy 2.5.3, Python 3.12.13`. `uv sync --python 3.12.13` installs it: Python 3.12.13 and the packages locked in `uv.lock`. Under another Python patch release or another package version `run` rejects the request with `unknown_reference`, because the request names another engine version than the present one; nothing runs. The engine version is part of every run response, and `walk.result.json` holds the SHA-256 of the responses, so its hash depends on the exact engine; the signature tables do not name it. The hashes were computed from fresh clones of both repositories, this one at commit `45f7f064e878d600e3b736e2a74643485746605a`, and are confirmed on one machine, the author's, under Linux on x86-64; whether other hardware gives the same bytes is not yet checked. `DELTARECON_ORACLE=1 uv run pytest tests/test_oracle.py -q` runs the reproduction in a temporary folder and checks every listed hash; without the variable only the published files are checked.

The earlier bare runner, which projects every model point and prints one SHA-256 over all result frames, moved to `delib-history` as `tools/run_release.py`, together with the portfolio builder and the test that pins the result hash of release N.

## Stage contracts

[`contracts/v2/`](contracts/v2/README.md) describes the stage `liability_cashflow` by three contracts that any calculation engine can implement: run, changes and compare. A domain reference names the quantities, their units and signs, and the time basis. A fourth file, `localise.md`, is no stage contract and no engine implements it: it fixes the walk and the search, procedures of the tool built on the three, and their results. The pack stands alone and names no engine and no implementation language. It holds the contract text, JSON schemas, and small synthetic examples of accepted and rejected input.

The tool writes contract version 2.0 and reads documents of 1.0 and 2.0, each against the schemas of its own version. A run record written under 1.0 serves as input to `regression`, `derive`, `walk`, `search`, and a comparison of recorded runs, but `replay` rejects it with `unsupported_version`. [`contracts/v2/README.md`](contracts/v2/README.md#changes-from-10) lists the changes from 1.0.

The pack is a specification. `degelmann.deltarecon` implements the run contract and the changes contract for the reference model, and the compare contract for any two runs: the comparison reads documents and exports and knows no engine. A replay goes through the compare contract and writes a compare result.

| Capability | Specified in | Implemented |
|---|---|---|
| Stage identity, release identity and serialization | [`contracts/v2/README.md`](contracts/v2/README.md) | Yes, in `degelmann.deltarecon`. |
| Full and subset runs, per-model-point export, run record | [`contracts/v2/run.md`](contracts/v2/run.md) | Yes, in `degelmann.deltarecon`, with a replay of a recorded run. Subset runs with intermediate results come later. |
| Change manifest, combination rules, text-patch profile, revision profile, derived manifest | [`contracts/v2/changes.md`](contracts/v2/changes.md) | The rules, the text-patch profile, and the manifest derived from the revision history of the reference model, one change per revision, and runs of a prefix of a derived manifest: yes, in `degelmann.deltarecon`. |
| Per-coordinate comparison, tolerance rule, parameter diff, signature table, replay criterion | [`contracts/v2/compare.md`](contracts/v2/compare.md) | Yes, in `degelmann.deltarecon`: the diff of two runs, the deviation signature table, the replay, and the regression run against a newer revision. |
| Walk over all states, contribution per revision and quantity, walk result; interval search, search result | [`contracts/v2/localise.md`](contracts/v2/localise.md) | Yes, in `degelmann.deltarecon`: the walk between two recorded results, and the interval search for a target, checked against the walk. ## The reference model and its limits

The reference model is `RLV_DE_S`, the Risikolebensversicherung (German term life) model from the `delib` library of [lifelib](https://github.com/lifelib-dev/lifelib). It is kept in the repository `delib-history`, in the folder `risikolebensversicherung/`. It projects monthly liability cash flows per model point. [modelx](https://github.com/fumitoh/modelx) reads and runs it.

Read every result from this model with these limits in mind:

- It is a demonstration of mechanics, not a valuation model. Upstream marks the library as a draft.
- The biometric tables are proxies. The mortality table is a Gompertz-form stand-in for DAV 2008 T, which is not public and is not shipped. Lapse rates are upstream's own assumptions.
- The cash flows are gross and undiscounted.
- The statutory references in the model's documentation are unverified upstream.
- DeltaRecon claims no HGB reserve, no Zinszusatzreserve and no profit participation from this model.

The portfolio holds upstream's 14 model points unchanged, plus 336 generated points, 24 variants of each. A variant keeps its template's product features and varies term, issue age, sex, smoker status, sum assured, premium frequency and, for two lives, the age gap and the second life's smoker status. One third of the generated points are in force, after one completed year, at 40 and 70 percent of the term, and in the final year; the others are new business. Each dimension is balanced within a template and mixed independently of the others, so a change in one input can be told apart from the others. Generated points stay inside upstream's documented product envelope (issue age 18 to 65, end age at most 75, term 5 to 40 years) and reach its edges.

The portfolio is synthetic and contains no client data. It is built to exercise the model's mechanics, not to resemble a real book: in-force points carry issue dates back to 1987, and the model prices all of them on its one current basis.

## Upstream attribution

This repo holds no file of lifelib. The reference model repository `delib-history` does: at release N the model files and five of its six input CSVs are copied byte for byte from lifelib at commit `fb1d195ab5423031cfd6d2548fe25a86b76cd0a1`, under the MIT licence, "Copyright (c) 2022 lifelib Developers". The sixth CSV, `model_point_table.csv`, extends upstream's file. Later commits of `delib-history` change some of these files; they are the changes that a derived manifest lists. `UPSTREAM.md` in the folder `risikolebensversicherung/` of `delib-history` records the details.
