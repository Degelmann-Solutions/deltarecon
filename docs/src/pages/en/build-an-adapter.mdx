<StepCard steps={frontmatter.steps} anchor="class">

Your connection, the <Term id="adapter">adapter</Term>, is one {cls} in a Python module. The module lies in a folder of your choice; it need not be a part of DeltaRecon. The protocol is the file `degelmann/deltarecon/protocol.py`. It needs the standard library of Python alone, so your module can import the types of the protocol from it.

In every step this page shows how the connection of the <Term id="reference-model">reference model</Term> solves the part, with lines of `degelmann/deltarecon/engines/reference_model.py`.

DeltaRecon calls your {cls} with the number of worker processes as its one optional argument: with no argument when the command gives no `--workers`, with `N` for `--workers N`, and with 1 for `request` and `derive`, which project no model point. An engine that has no use for worker processes accepts the argument and ignores it.

The {cls} first says four things about itself. They are attributes, not operations.

<StepCard steps={frontmatter.steps} anchor="releases">

DeltaRecon knows no file and no repository of your engine. It names a release by a release identity: a label and a set of references that only your connection reads. Four operations belong to this. None of them restores or writes anything.

The reference model keeps its history in a Git repository. From such a history a connection needs four things: to name a revision, to read the files of a revision, to list the revisions between two releases on the main line, and to say what each of them touches. This step needs the first two; step 5 needs the other two.

The connection of the reference model reads the repository with a library, `dulwich`, and starts no Git program, so none has to be installed. An engine whose history is not in Git answers the same four questions in its own way.

<Callout tag="If you know Git" title="The same questions as Git commands">

The connection of the reference model runs none of these commands. Each line names the command that answers the same question, and where the connection differs from it.

{git('git rev-parse --verify <name>^{commit}')} Name a revision: the full hash of the commit that a hash, a branch, a tag or `HEAD` names. The connection takes no suffix such as `HEAD~1`.

{git('git ls-tree -r <commit>')} List the files of a revision. The connection refuses a revision that holds anything other than regular files.

{git('git show <commit>:<path>')} Read one file of a revision. The connection writes every file of the revision into a new folder, byte for byte; it uses no archive and no working tree.

{git('git log --first-parent --reverse <older>..<newer>')} List the revisions between two releases on the main line, the oldest first. The connection refuses two revisions of which the older does not lie on the main line of the newer.

{git('git diff --name-only --no-renames <parent> <commit>')} Say which paths a revision touches, against the revision before it.

{git('git fetch --unshallow')} Complete a clone whose history is cut off, a shallow clone. The connection refuses to read the history from such a clone and names this command.

</Callout>

<StepCard steps={frontmatter.steps} anchor="open">

`open` does the work of a run. It restores the state of the release into a scratch folder, applies the enabled changes there, and gives back the opened release. DeltaRecon uses the result in a `with` statement of Python and reads the opened release inside it.

What the folder of the histories holds is never altered. The scratch folder is created in the temporary folder of the system, and its name starts with `deltarecon-`.

DeltaRecon hands over the enabled changes in the order in which they apply, and with them the folder of the <Term id="change-manifest">change manifest</Term>. Each change is of a kind that your engine named in step 1. For revisions the engine restores the state after the last enabled revision; `hold` names the kinds that it then takes from the release of the request instead.

A revision of another history than its own is a change your engine cannot apply: it rejects it with `unsupported_realisation` before it restores anything. A change that does not apply is rejected with `invalid_manifest`. Any other error ends the run with the outcome `error`.

<StepCard steps={frontmatter.steps} anchor="session">

The opened release is a second, small {cls}. It stands for one state of the model and answers what a run asks: which model points there are, and the projection of each, with one <Term id="value">value</Term> per quantity and period. It also gives the parameters of the release, which the <Term id="record">record</Term> of a run holds.

It has two attributes and three operations. Two more operations are optional. The names of the quantities must be those that your engine names for the stage in step 1: DeltaRecon checks them.

<StepCard steps={frontmatter.steps} anchor="history">

`walk` and `search` compute the states between two releases one by one. For this they need the history between the two as single revisions, and a name for the state after each.

`history` lists every revision on the main line after the older release, up to and including the newer one, the oldest first. Each comes with its message as it was written and with the <Term id="class">classes</Term> of the paths it touches: data, parameter, code. What the main line is, your engine defines; in Git it is the chain of first parents. The list is empty when both releases name one revision.

When the older revision does not lie on the main line of the newer one, the operation rejects the two with `unrelated_revisions`.

<StepCard steps={frontmatter.steps} anchor="select">

Seven commands load an engine: `request`, `run`, `replay`, `regression`, `derive`, `walk` and `search`. Each takes the engine from the first of three places that names one, and looks for its module in a folder that you name.

When a selection cannot be loaded, the command says in one line what is wrong, writes nothing and ends with <Term id="exit-status">exit status</Term> 2. This holds for a folder that is no folder, a selection that is not of the form `<module>:<class>`, a module that is not found, a name in the module that is no class, and a class that does not take the number of worker processes as its argument.

<Callout tag="Known limits" title="Four faults that end in a traceback">

In this release DeltaRecon answers four faults of a connection with a traceback of Python and exit status 1, not with a message of its own. That is a limit of this release, not an error in how you call the command. The last line of the traceback names the cause.

The module of your connection raises another error than a failed import while it is loaded, for example a syntax error.

Your class raises an error of its own when it is called with the number of worker processes.

Your class lacks a member of the protocol.

The history that your connection gives breaks the protocol: its kind is not a name in small letters, its revisions do not lead from the older to the newer release, or a revision carries a class other than data, parameter and code.

</Callout>

`request` prints the path of the request it wrote. `run` prints `outcome: succeeded`, the number of model points, the number of rows of the results and their SHA-256, and the paths of the three files it wrote. With a second run, of another revision, you can compare two results. `regression`, `replay`, `walk` and `search` write their compare requests themselves and run them. You write a compare request yourself only for `compare`, the comparison of two runs by hand. It is a JSON file with these members:
