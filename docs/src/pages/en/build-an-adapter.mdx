<StepCard steps={frontmatter.steps} anchor="class">

Your connection, the <Term id="adapter">adapter</Term>, is a {cls} in a Python module. The module lies in a folder of your choice; it need not be a part of DeltaRecon. The <Term id="protocol">protocol</Term> is the file `degelmann/deltarecon/protocol.py`. It needs the standard library of Python alone, so your module can import the types of the protocol from there: `StageDeclaration`, `DomainReference`, `Revision` and `History`, the errors `Rejection`, `UsageError` and `ModelPointFailure`, and the constant `SCRATCH_PREFIX`.

Your module needs two <span data-no-term>classes</span>: that of the <Term id="engine">engine</Term>, with four statements and seven operations (steps 1 to 3 and 5), and a small one for an opened <Term id="release">release</Term> (step 4).

This page goes through each part on its own. For each part you see its signature from the protocol, what DeltaRecon hands to you, what you give back and which errors you report. A part to unfold shows how the connection of the <Term id="reference-model">reference model</Term> does it, with lines of `degelmann/deltarecon/engines/reference_model.py`.

<Member name="Call the class" code="__init__" signature="constructor">

DeltaRecon calls your {cls} with the number of worker processes as its one, optional argument. The signature is that of the reference model; your {cls} takes the same argument.

<Part label={GET}>

- `workers`: `None` when the command names no `--workers`; the number `N` with `--workers N`; and 1 for `request` and `derive`, which project no <Term id="model-point">model point</Term>.

</Part>

<Part label={DO}>

Keep the number when your engine can project model points in several processes. Without an argument your engine decides itself; DeltaRecon does not read the variable `DELTARECON_WORKERS`. An engine that has no use for worker processes accepts the argument and ignores it.

</Part>

<Member name="The stages your engine offers" code="stages" of="Engine">

An attribute of the {cls}: one entry per stage, under the name of the stage. A stage is one kind of result that your engine computes, with fixed <Term id="quantity">quantities</Term>.

<Part label={SET}>

- The key is the name of the stage, which the request and the option `--stage` name.
- The <span data-no-term>value</span> is a `StageDeclaration(domain_reference, quantities)`.
- `domain_reference` is a `DomainReference(id, version)`: the reference to the domain reference of the stage, the text that says what its quantities, their units and signs, and the time basis mean. Both members are strings of your choice that are not empty; `version` changes only when the text changes meaning.
- `quantities` are the names of the quantities in the order of that text.

</Part>

<Part label={USE}>

DeltaRecon accepts a request only for a stage named here. It checks the names of the quantities that an opened release declares (step 4) against the names here, and it writes the reference into every response of the stage.

</Part>

<Fold summary={REF}>

<CodeExcerpt id="class-statements">

</CodeExcerpt>

The reference model offers one stage, `liability_cashflow`. Its domain reference is the file `contracts/v3/domain/liability_cashflow.md` of the repository.

An attribute of the {cls}: a set of names.

<Part label={SET}>

- `revision`, when your engine can apply a revision of its own <Term id="history">history</Term>. `walk` and `search` need it: they compute each <Term id="state">state</Term> as a release with enabled revisions.
- `text_patch`, when it can apply a text patch that a <Term id="change-manifest">change manifest</Term> brings along as a file.

</Part>

<Part label={USE}>

Every enabled change that `open` is given (step 3) is of a kind that stands here.

</Part>

<Fold summary={REF}>

The reference model names both kinds, `text_patch` and `revision`. The line stands in the excerpt at `stages`.

</Fold>

</Member>

<Member name="What one revision fixes" code="determines" of="Engine">

An attribute of the {cls}: the kinds of reference of a release that one revision of your history determines.

<Part label={SET}>

The names of the kinds, as they stand in a release identity (step 2, `describe`). For the reference model one revision fixes the code (`code_state`), the parameters (`parameter_set`) and the input data (`input_data`).

</Part>

<Fold summary={REF}>

The reference model names the three kinds `code_state`, `parameter_set` and `input_data`. The line stands in the excerpt at `stages`.

An attribute of the {cls}: the kinds of reference that can stay as the request names them while revisions are applied.

<Part label={SET}>

- The key is a kind of reference, for example `input_data`.
- The <span data-no-term>value</span> is the set of the <Term id="class">classes</Term> of the paths that carry this kind, for example `data`.

<Part label={USE}>

A <Term id="regression">regression</Term> computes the newer revision on the input data of the <Term id="run">recorded run</Term>. For that DeltaRecon names in `hold` the kinds that are held (steps 3 and 5); each stands here.

</Part>

The reference model can hold the input data: `input_data` with the class `data`, the model point table. The line stands in the excerpt at `stages`.

<StepCard steps={frontmatter.steps} anchor="releases">

DeltaRecon knows no file and no repository of your engine. It names a release by its release identity: a label and a set of references that only your connection reads. In the signatures it is called `release` and is a `dict` of Python. Four operations belong to it. None of them restores or writes anything.

The reference model keeps its history in a Git repository. From such a history a connection needs four things: name a revision, read the files of a revision, list the revisions between two releases on the <Term id="main-line">main line</Term>, and say what each of them touches. This step needs the first two, step 5 the other two.

The connection of the reference model reads the repository with a library, `dulwich`, and starts no Git program; so none has to be installed. An engine whose history is not in Git answers the same four questions in its own way.

<Part label={GET}>

- `given`: the folder that the option `--repositories` names, or `None` when the command names none.

<Part label={GIVE}>

A `Path`: the folder given, else the default of your engine. You read nothing beyond the lookup, and the folder need not exist.

</CodeExcerpt>

<Member name="Describe a release by its revision" code="describe" of="Engine">

`request` calls this operation and writes its result into the request. It turns a revision, as a person names it, into the complete release identity.

<Part label={GET}>

- `stage`: the stage of the request, one of `stages`.
- `label`: the label that the command is given with `--label`, for example `N`.
- `revision`: the revision as the command is given it with `--revision`. How a revision is named is your engine's matter, for example by a hash, a branch or a tag.
- `options`: the options of the engine from `--engine-option`, by key; empty when the command names none.
- `repositories`: the folder from `repositories_folder`.
- `input_revision`: `None`, or the identifier of a revision as `input_revision` gives it. The input data are then those of that revision. You take the identifier as it is and do not resolve it again.

</Part>

<Part label={GIVE}>

A `dict` with two keys: `label`, the label given, and `references`, a list of references. Each reference is a `dict` with `kind` and `value`, a <span data-no-term>value</span> that only your connection reads. The list names the state completely: so that `resolve` and `open` find it again from it.

</Part>

<Part label={REPORT}>

- `UsageError` for an option that your engine does not take, a key or a <span data-no-term>value</span>, before you read the revision.
- `Rejection("unknown_reference", …)` when `revision` names nothing.

</Part>

<Fold summary={REF}>

The reference model writes four references: one each for code, parameters and input data, all with the full hash of the revision, and one for the version of the core of the engine. With `input_revision` only the reference of the input data names the other revision; that is how a regression describes the state N+1 on the input data of release N.

<Member name="Check that a release can be restored" code="resolve" of="Engine">

`request` checks the release identity with it before it writes the request. `replay`, `walk` and `search` check a recorded release with it before they compute.

<Part label={GET}>

- `stage`: the stage of the request, one of `stages`.
- `release`: a release identity, in the form that `describe` gives back.
- `repositories`: the folder from `repositories_folder`.

</Part>

<Part label={GIVE}>

Nothing. The operation ends without an error when the release identity names a state of the stage that your engine can restore.

</Part>

<Part label={REPORT}>

- `Rejection("unknown_reference", …)` when the references cannot be resolved.

</Part>

<Member name="Name the revision of the input data" code="input_revision" of="Engine">

`regression` asks with it on which input data a recorded run was computed, and then has the newer revision described with those input data.

<Part label={GET}>

- `release`: a recorded release identity. It may come from another version of the core of your engine.

</Part>

<Part label={GIVE}>

A string: the identifier of the revision that the release takes its input data from, in the form that `describe` takes as `input_revision`.

</Part>

<Part label={REPORT}>

- `Rejection("unknown_reference", …)` when `release` names no state that your engine can read.

<Callout tag="If you know Git" title="The same questions as Git commands">

The connection of the reference model runs none of these commands. Each line names the command that answers the same question, and where the connection differs from it.

{git('git rev-parse --verify <name>^{commit}')} Name a revision: the full hash of the commit that a hash, a branch, a tag or `HEAD` names. The connection takes no suffix such as `HEAD~1`.

{git('git ls-tree -r <commit>')} List the files of a revision. The connection refuses a revision that holds anything but regular files.

{git('git show <commit>:<path>')} Read one file of a revision. The connection writes every file of the revision into a new folder, byte for byte; it uses no archive and no working tree of the repository.

{git('git log --first-parent --reverse <older>..<newer>')} List the revisions between two releases on the main line, the oldest first. The connection refuses two revisions of which the older one does not lie on the main line of the newer one.

{git('git diff --name-only --no-renames <parent> <commit>')} Say which paths a revision touches, against the revision before it.

{git('git fetch --unshallow')} Complete a clone whose history is cut off. From such a clone the connection does not read the history, and it names this command.

</Callout>

<StepCard steps={frontmatter.steps} anchor="open">

`open` does the work of a run. It restores the state of the release in a scratch folder, applies the enabled changes there and gives back the opened release. DeltaRecon uses the result in a `with` statement of Python and reads the opened release inside it.

What the folder of the histories holds is never altered. The scratch folder is created in the temporary folder of the system, and its name begins with `deltarecon-`, the <span data-no-term>value</span> of `SCRATCH_PREFIX`.

<Member name="Open a release for a run" code="open" of="Engine">

The operation is a context manager: it hands out the opened release and clears the scratch folder away when the `with` statement ends. The simplest way to write it is a generator with `@contextmanager` of `contextlib`.

<Part label={GET}>

- `stage`: the stage of the request, one of `stages`.
- `release`: the release identity of the request, in the form of `describe`.
- `enabled`: the enabled changes in the order in which they are applied; empty for a run without changes. Each is an entry of a change manifest, and its `realisation.type` is a kind of `realisations`.
- `manifest_dir`: the folder of the change manifest, which the paths of its files are relative to; `None` when no change is enabled.
- `repositories`: the folder from `repositories_folder`.
- `hold`: the kinds of reference that you take from `release` instead of from the last enabled revision; each is a kind of `holdable`. Empty when nothing is held.

</Part>

<Part label={DO}>

- Without enabled changes you restore the state that `release` names.
- For changes of the kind `revision` you restore the state after the last enabled revision. The kinds in `hold` you take from `release`.
- Restore the state in a new folder in the temporary folder of the system whose name begins with `SCRATCH_PREFIX`.

</Part>

<Part label={GIVE}>

The opened release: an object of your second {cls} (step 4).

</Part>

<Part label={REPORT}>

- `Rejection("unsupported_realisation", …)` for a revision whose `source` is not the history of your engine, before you restore anything.
- `Rejection("invalid_manifest", …)` for a change that does not apply.
- Any other error ends the run with the outcome `error`.

</Part>

It has two attributes and three operations. Two further operations are optional.

<Member name="Project a target only" code="project_target" of="Session" tag="optional">

<StepCard steps={frontmatter.steps} anchor="select">

Seven commands load an engine: `request`, `run`, `replay`, `regression`, `derive`, `walk` and `search`. Each takes the engine from the first of three places that names one, and looks for its module in a folder that you name.

When a selection cannot be loaded, the command says in one line what is wrong, writes nothing and ends with <Term id="exit-status">exit status</Term> 2. This holds for a folder that is no folder, a selection that is not of the form `<module>:<class>`, a module that is not found, a name in the module that is no class, and a class that does not take the number of worker processes as its argument.

<Callout tag="Known limits" title="Four faults that end in a traceback">

In this release DeltaRecon answers four faults of a connection with a traceback of Python and exit status 1, not with a message of its own. That is a limit of this release, not an error in how you call the command. The last line of the traceback names the cause.

The module of your connection raises another error than a failed import while it is loaded, for example a syntax error.

Your class raises an error of its own when it is called with the number of worker processes.

Your class lacks a member of the protocol.

The history that your connection gives breaks the protocol: its kind is not a name in small letters, its revisions do not lead from the older to the newer release, or a revision carries a class other than data, parameter and code.

</Callout>
